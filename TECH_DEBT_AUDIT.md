# Tech Debt Audit — Sift (dj-assistant-m6a, branch `m6a-discogs`)
Generated: 2026-07-15

## Executive summary

- The codebase is in genuinely good shape for its size (~30k LOC: 19.7k Rust + 10.5k TS). Panic-safety, error handling, and type discipline on the audited hot paths are solid — several suspected issues (unwrap counts, `any` usage, innerHTML-in-loop) turned out to be false alarms on verification. That itself is a finding worth stating, per the audit protocol's required "looks bad but is fine" section.
- The one real risk concentration is the **Rekordbox `master.db` write surface** (`rekordbox_masterdb.rs`, 2740 lines) — the exact area CLAUDE.md already flags as high-stakes (live third-party database, no do-over on corruption). It has an error-handling inconsistency (F01) and zero logging anywhere in the file (F02).
- `frontend/filing.ts` (2150 lines) is now the largest, least-split frontend file — structurally the same "five responsibilities in one module" shape that `sift-live.ts` had before its documented 2026-07-13 split into `rekordbox-view.ts`/`queue-panel.ts`/`batch-panel.ts`. No split is currently planned for it (F03).
- ~20 unnecessary `export` keywords in `rekordbox-view.ts` and 7 other files are pure mechanical cleanup — module-private state/helpers exported for no reason knip can detect (F04–F11).
- 2 confirmed dead exports (`rescanSource`, `fmtDur`) and ~13 dead files, mostly outside `frontend/` (archived design-handoff exports, a `remember` tool artifact) (F12–F15).
- `cargo clippy --all-targets` is clean at the project's actual gate (`-D warnings`, 0 warnings). Pedantic mode surfaces 490 warnings, dominated by cast-precision/pass-by-value style noise typical of DSP code — not a debt signal, noted for completeness only.
- `npm audit` (prod deps) and dependency versions are clean/current — no action needed, consistent with CLAUDE.md's documented 2026-07-01 dependency audit.
- No `TODO`/`FIXME`/`HACK` markers anywhere in `src-tauri/src` or `frontend` — the project's own docs (`ressources-externes.md`/`INDEX.json`) are doing the job a TODO backlog usually does, and mostly succeeding: only one tracked count (dead-code allowlist size) was found slightly stale.
- Duplicated `conn.lock().map_err(|e| e.to_string())?` boilerplate appears ~40+ times across `ipc*.rs` files — low severity, easy extraction (F16).
- Nothing found in dependency/config, test, or documentation-drift dimensions material enough to report beyond what's already tracked in `docs/ressources-externes.md`.

## Architectural mental model

Sift is a Tauri v2 desktop app (Rust backend, vanilla-TS frontend, no framework) for DJs to vet, dedupe, tag, and file downloaded tracks, with a deep secondary feature set for repairing/syncing a live Rekordbox `master.db` (SQLCipher-encrypted, external app's database — Sift never owns it, only patches it under strict backup/verify/rollback discipline). The backend is a flat module layout (by design, per `docs/superpowers/specs/2026-07-13-architecture-evolution-design.md` — directory restructuring is explicitly deferred pending frontend-side proof of value) split into: ingestion (`scanner`/`watcher`/`sources`/`worker`/`queue`), analysis (`analysis/*`, pure-Rust Symphonia decode + rustfft), the filing pipeline (`encode`/`naming`/`tagging`/`filing`/`actions`), dedup (`dedup`/`fingerprint`), Discogs metadata (`metadata/*`), library browsing (`library`/`genres`), and the Rekordbox integration (`rekordbox_masterdb`/`rekordbox_repairs`/`rekordbox_xml`, the largest and riskiest surface). The frontend mirrors this with one file per screen/concern, recently detangled from a single 2083-line `sift-live.ts` god file (Phase 1 of a documented 3-phase architecture evolution, completed 2026-07-13/14) down to a 519-line entrypoint, with three extracted controllers.

This matches the README/CLAUDE.md's stated model closely — no contradiction found. The one gap: the architecture evolution plan that motivated splitting `sift-live.ts` doesn't yet list `filing.ts` as a target, even though it's now larger (2150 lines) than `sift-live.ts` was pre-split relative-complexity-wise (five distinct responsibilities per the frontend audit below), and was never part of that phased plan's scope.

## Top 5 — if you fix nothing else, fix these

1. **F02 — Add logging to `rekordbox_masterdb.rs`.** This file is where a bug becomes "Antoine's real Rekordbox library got corrupted" with zero server-side trail to diagnose it after the fact. Minimum viable fix: `log::error!` on every branch that currently only builds a `MasterDbError` for the write/verify/rollback trio (`with_masterdb_write`, `sync_track_artwork`, `sync_track_metadata`, `repair_track_path`, `dedup_playlist_group`). This is the single highest-leverage fix in the audit given CLAUDE.md's own risk framing.
2. **F01 — Fix the artwork-rollback error swallow.** Same file, same failure class as F02 but a concrete correctness gap: a failed rollback currently looks identical to a failed write to both the log (nothing) and the caller (generic write error), hiding the fact that the filesystem may now be in a half-restored state.
   ```rust
   // rekordbox_masterdb.rs:1341-1344, current:
   if let Err(write_err) = write_result {
       restore_all(&backups).ok();
       return Err(write_err);
   }
   // fix, mirroring with_masterdb_write (lines 933-940):
   if let Err(write_err) = write_result {
       return Err(match restore_all(&backups) {
           Ok(()) => write_err,
           Err(restore_err) => MasterDbError::WriteVerificationFailedRollbackFailed(
               format!("{write_err}; rollback also failed: {restore_err}")
           ),
       });
   }
   ```
3. **F03 — Track `filing.ts` as the next split candidate.** Not urgent today (no bugs found in it), but it's quietly become the largest, least-decomposed file in the frontend, and the project already has a proven playbook (the `sift-live.ts` Phase 1 split) for exactly this shape. Cheapest time to act is before it grows further, not after.
4. **F04/F05 — Batch-drop the 19 unnecessary `export`s in `rekordbox-view.ts`.** Zero risk, ~20 minutes, immediately clarifies the file's real public surface (currently obscured by 19 exports that look like cross-module API but aren't).
5. **F16 — Extract the `lock_conn` helper.** Small, but it's copy-pasted at every single IPC entry point in the busiest 3 files; one bug in the pattern (e.g. wrong error message) currently has to be fixed 40+ times instead of once.

## Things that look bad but are actually fine

1. **977 `.unwrap()` / 240 `.expect()` calls repo-wide** looked alarming at first grep, but exhaustively filtering each occurrence against its file's `#[cfg(test)] mod tests` boundary shows essentially all of them are confined to test code (fixtures, `tempfile::tempdir().unwrap()`, in-memory SQLite connections). Spot-checked `actions.rs` (211 raw hits → 1 in production code, guarded — see #2 below), `rekordbox_masterdb.rs` (198 raw hits → 5 in production code, all infallible — see #3), `filing.ts`'s Rust counterpart `filing.rs` (121 raw hits → 0 in production code). Zero unguarded panics found in production code paths across `actions.rs`, `filing.rs`, `rekordbox_repairs.rs`, `ipc_library.rs`, `rekordbox_masterdb.rs`, `library.rs`, `tagging.rs`, `sources.rs`, `fingerprint.rs`, all of `analysis/*.rs`, `usb_format/*.rs`, and `metadata/*.rs`. Naive tooling (or a naive audit) would have reported this as a top finding; it isn't one.
2. **`actions.rs:670` `rows.iter().map(|r| r.0).max().unwrap()`** reads like an unguarded unwrap on possibly-empty data, but lines 666-668 explicitly `return Err(...)` if `rows.is_empty()` immediately before this line. Guarded.
3. **`rekordbox_masterdb.rs:503-505,704-705` `.expect("HMAC-SHA512 accepts any key length")`** and **`:591` `try_into::<[u8;16]>().expect("iv is 16 bytes")`** — HMAC-SHA512 has no key-length restriction per the algorithm spec, and the key is always a fixed 32-byte array; the IV slice is already sliced to exactly 16 bytes two lines above. These literally cannot fail — `.expect()` with a message stating the invariant is the idiomatic Rust choice here, not a debt item.
4. **SQL table-name interpolation via `format!` in `rekordbox_masterdb.rs:1120,1165`** looks like a SQL-injection vector at a glance (`format!("SELECT ... FROM {table} ...")`), but `table` is validated against a hardcoded 3-element allowlist (`FK_TABLES`, line 1082) before use, never from external/user input. No injection surface.
5. **`ipc.rs:297-303` `if let Ok(conn) = conn.lock() { ... let _ = conn.execute(...) }`** silently drops both the lock result and the write result — looks like the same anti-pattern as F01/F02, but this is an explicit best-effort self-heal of the analysis cache (the surrounding comment says so directly); failing here just means the next open recomputes instead of hitting cache. No data-loss risk, unlike F01 which discards the outcome of a *recovery* action after a real write failure.
6. **Rekordbox `ImagePath` path-traversal risk**, flagged by the 2026-07-10 security audit at confidence 7/10 as an unresolved followup (`docs/superpowers/reviews/2026-07-10-security-audit-m6a-discogs.md`), is already fixed: commit `ef99ed7`'s `resolve_artwork_variants` (`rekordbox_masterdb.rs:1202`) does component-wise path joining that rejects `..` and drive-prefix escapes, returning `ArtworkPathEscapesRoot` (line 233) instead of resolving silently, with a regression test. Not an open item — the audit doc should be marked resolved.
7. **`filing.ts`'s many `innerHTML =` assignments** look like a violation of CLAUDE.md's "no innerHTML in a loop on high-frequency events" convention at first grep, but every occurrence triggers on a discrete user action (track open, click, identify result) — none are bound to `mousemove`/`scroll`/`resize`/progress events. The genuinely high-frequency handlers in the codebase (`report-view.ts:289,988`, spectrogram/waveform hover) correctly mutate only `style`/canvas pixels, never `innerHTML`, exactly as the convention prescribes.
8. **`shared/contracts.ts`'s "unused" exported types** (`Spectrogram`, `Confidence`, `LibraryFolder`, `DupGroupMember`, `GenreCount`, `PlaylistDuplicateEntryDto`) flagged by knip aren't dead — each is used as a field type of another exported interface in the same file, and TS consumers access those fields structurally without importing the type name. This is knip's known blind spot for structural typing, not a real problem.
9. **`cargo clippy --all-targets -- -W clippy::pedantic` reporting 490 warnings** looks like a wall of debt, but the project's actual quality gate is default clippy at `-D warnings` (per CLAUDE.md's documented lint command), which passes clean. Pedantic-mode noise here is dominated by cast-precision-loss and pass-by-value lints inherent to numeric DSP code (`analysis/*.rs`) — expected and not worth chasing without a specific bug driving it.
